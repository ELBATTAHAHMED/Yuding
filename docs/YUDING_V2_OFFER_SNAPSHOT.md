# Yuding V2 — Immutable Offer Snapshot Architecture (Phase 35)

## Overview
Phase 35 implements server-authoritative, tamper-proof, immutable offer snapshots for bookings. When a user selects a travel offer (Flight, Hotel, Activity, Transfer, or Train), an immutable snapshot of what was selected and priced during discovery is captured and persisted in schema `booking.offer_snapshots`.

---

## 1. Core Architecture & Principles

1. **Exact 1:1 Snapshot Relationship**:
   - Each booking has at most one immutable offer snapshot (`UNIQUE (booking_id)` constraint).
   - Once attached, the snapshot is strictly immutable (`updatable = false` on all entity columns).

2. **Server-Authoritative Selection Flow**:
   - Upstream search results generated by `travel-service` automatically issue an opaque `selectionRef` (UUID) stored in a short-lived cache (Redis with in-memory fallback, TTL: 15 minutes).
   - Frontend clients **never author or submit prices, currencies, provider names, or room/flight details**. Clients submit only the opaque `selectionRef`.
   - `reservation-service` resolves the `selectionRef` directly from `travel-service` via internal Feign client (`/internal/travel/offers/resolve/{selectionRef}`).

3. **Cryptographic Integrity & Verification**:
   - Deterministic SHA-256 hash (`snapshot_hash`) computed across canonicalized fields: `bookingId`, `provider`, `providerOfferId`, `productType`, `providerAmount`, `providerCurrency`, `displayAmount`, `displayCurrency`, `exchangeRate`, `capturedAt`, and sorted `selectedDetails` JSON.
   - Any tampering or field mismatch invalidates the hash.

4. **Lifecycle & Mutability Rules**:
   - Offer snapshots can only be attached to a booking in `DRAFT` status.
   - Attempting to attach a snapshot to non-DRAFT bookings returns `400 Bad Request`.
   - Attempting to overwrite an existing snapshot returns `409 Conflict`.

## 2. Database Schema (Flyway V15)

```sql
-- Logical schema: booking
CREATE TABLE IF NOT EXISTS booking.offer_snapshots (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    booking_id UUID NOT NULL,
    provider VARCHAR(64) NOT NULL,
    provider_offer_id VARCHAR(255) NOT NULL,
    product_type VARCHAR(32) NOT NULL,
    selected_details JSONB NOT NULL,
    provider_amount NUMERIC(12, 2) NOT NULL,
    provider_currency VARCHAR(3) NOT NULL,
    display_amount NUMERIC(12, 2),
    display_currency VARCHAR(3),
    exchange_rate NUMERIC(18, 6),
    exchange_rate_date DATE,
    exchange_rate_provider VARCHAR(64),
    captured_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    provider_expires_at TIMESTAMPTZ,
    snapshot_expires_at TIMESTAMPTZ,
    snapshot_hash VARCHAR(64) NOT NULL,

    CONSTRAINT fk_offer_snapshots_booking
        FOREIGN KEY (booking_id)
        REFERENCES booking.bookings(id)
        ON DELETE CASCADE,

    CONSTRAINT uk_offer_snapshots_booking_id UNIQUE (booking_id),
    CONSTRAINT chk_offer_snapshots_product_type CHECK (product_type IN ('FLIGHT', 'HOTEL', 'ACTIVITY', 'TRANSFER', 'TRAIN')),
    CONSTRAINT chk_offer_snapshots_provider_currency CHECK (provider_currency ~ '^[A-Z]{3}$'),
    CONSTRAINT chk_offer_snapshots_display_currency CHECK (display_currency IS NULL OR display_currency ~ '^[A-Z]{3}$'),
    CONSTRAINT chk_offer_snapshots_hash_len CHECK (length(snapshot_hash) = 64)
);

CREATE INDEX idx_offer_snapshots_booking_id ON booking.offer_snapshots(booking_id);
CREATE INDEX idx_offer_snapshots_provider ON booking.offer_snapshots(provider, provider_offer_id);
CREATE INDEX idx_offer_snapshots_captured_at ON booking.offer_snapshots(captured_at);
```

## 3. Endpoints & API Contract

### A. Internal Offer Resolution (`travel-service`)
- **Path**: `GET /internal/travel/offers/resolve/{selectionRef}`
- **Security**: Service-to-service internal communication (not routed to public gateway).
- **Response**: `200 OK` with `ResolvedOfferDto` or `404 Not Found` if expired/unknown.

### B. Draft Creation with Snapshot (`reservation-service`)
- **Path**: `POST /bookings`
- **Request Body**:
  ```json
  {
    "productType": "FLIGHT",
    "selectionRef": "d3b07384-d113-4f95-bc65-0210e30dcd47"
  }
  ```
- **Response**: `201 Created` with `Location: /bookings/YUD-XXXXXXXX` and attached `offerSnapshot` projection.

### C. Explicit Snapshot Attachment (`reservation-service`)
- **Path**: `POST /bookings/{reference}/offer-snapshot`
- **Request Body**:
  ```json
  {
    "selectionRef": "d3b07384-d113-4f95-bc65-0210e30dcd47"
  }
  ```
- **Response**: `200 OK` with updated `BookingResponseDto` including `offerSnapshot`.

### D. Booking Lookup (`reservation-service`)
- **Path**: `GET /bookings/{reference}`
- **Response**: `200 OK` containing booking summary, lifecycle status, public reference, and embedded `offerSnapshot` (if attached). Internal primary keys (`id`, `booking_id`) are excluded.

---

## 4. Security & Isolation

- **IDOR Protection**: All snapshot queries and mutations verify that the authenticated user owns the target booking (`userId`), with administrative override (`ROLE_ADMIN`).
- **Data Integrity**: JSON details are validated and stored as PostgreSQL `JSONB`.
- **Port Isolation**: External clients access booking and travel endpoints strictly via API Gateway (`http://localhost:8888`). Direct microservice ports remain internal.
